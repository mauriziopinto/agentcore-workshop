AgentCore Workshop TelcoCare

Lab 3 · Gateway e Identity

Colleghi l'agente al CRM di TelcoCare attraverso AgentCore Gateway, e vedi chi autentica chi a ogni passaggio. Venticinque minuti.

Concetto: AgentCore Gateway

Gateway espone degli strumenti con il protocollo MCP (Model Context Protocol) da un unico endpoint. Gli strumenti possono venire da una funzione Lambda, da un'API descritta in OpenAPI, da un server MCP esistente o da altre fonti. L'agente non sa dove sta il codice di ogni strumento: vede solo un elenco di strumenti MCP.

Il vantaggio è che lo stesso strumento serve a più agenti, e i controlli (chi può chiamare, con quali regole) stanno in un punto solo.

Il CRM di TelcoCare è una Lambda con quattro strumenti: get_cliente, get_fatture, apri_ticket ed emetti_accredito. I dati sono finti e fissi nel codice: tre clienti, C001, C002 e C003.

  1. Crea la Lambda del CRM con CloudFormation. Ci vuole circa un minuto.

    aws cloudformation deploy --stack-name telcocare-crm \
  --template-file ../risorse/lab3/crm-lambda.yaml --capabilities CAPABILITY_IAM

CRM_ARN=$(aws cloudformation describe-stacks --stack-name telcocare-crm \
  --query "Stacks[0].Outputs[?OutputKey=='CrmFunctionArn'].OutputValue" --output text)
echo $CRM_ARN

    La Lambda non ha un URL pubblico. La può chiamare solo chi ha il permesso IAM lambda:InvokeFunction, cioè il ruolo del Gateway che crei fra poco.

  2. Copia nel progetto lo schema degli strumenti. Per ogni strumento descrive nome, scopo e parametri: è quello che il modello legge per decidere quando usarlo.

    mkdir -p schemas
cp ../risorse/lab3/crm_tools.json schemas/

  3. Aggiungi un Gateway con autorizzazione IAM, poi la Lambda come target.

    agentcore add gateway --name strumenti --authorizer-type AWS_IAM

agentcore add gateway-target --gateway strumenti --target-configuration \
  "{\"name\":\"crm\",\"targetType\":\"lambdaFunctionArn\",\"lambdaFunctionArn\":{\"lambdaArn\":\"$CRM_ARN\",\"toolSchemaFile\":\"schemas/crm_tools.json\"}}"
    Attenzione Se hai aperto un terminale nuovo dopo il passo 1, la variabile CRM_ARN è vuota. Rilancia il comando CRM_ARN=$(...) del passo 1 prima di aggiungere il target.

  4. Collega l'agente al Gateway.

    cp ../risorse/lab3/gateway_client.py app/agent/gateway_client.py
cp ../risorse/lab3/main.py app/agent/main.py

    gateway_client.py crea un client MCP che firma ogni richiesta con le credenziali AWS del Runtime (firma SigV4). L'indirizzo del Gateway arriva dalla variabile AGENTCORE_GATEWAY_STRUMENTI_URL, che il deploy imposta nel Runtime. In main.py il client si aggiunge alla lista degli strumenti, accanto a calcola_rata.

    app/agent/main.py (estratto)
    tools.append(calcola_rata)

# Lab 3: gli strumenti del CRM arrivano dal Gateway
gateway = get_gateway_client()
if gateway:
    tools.append(gateway)
    Una trappola che abbiamo trovato Con il CLI 1.0.1 la variabile contiene solo l'indirizzo del Gateway, senza il percorso /mcp su cui risponde il server MCP. Il codice del tutorial ufficiale usa la variabile così com'è e la connessione fallisce con un errore poco chiaro (Failed to start MCP client). Il nostro gateway_client.py aggiunge /mcp se manca.

  5. Pubblica. Il deploy crea il Gateway, il suo ruolo IAM, il target e dà al ruolo del Runtime il permesso di chiamare il Gateway. Ci vogliono circa 2 minuti e mezzo.

    agentcore deploy

  6. Chiedi al Gateway l'elenco degli strumenti, con una chiamata MCP tools/list.

    agentcore invoke --gateway strumenti --path /mcp \
  --payload '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'
    Cosa dovresti vedere I quattro strumenti, con il nome del target davanti: crm___get_cliente, crm___get_fatture, crm___apri_ticket, crm___emetti_accredito.

  7. Controlla che il Gateway rifiuti chi non è autenticato. Questa chiamata non ha firma IAM.

    GATEWAY_URL=$(aws bedrock-agentcore-control get-gateway \
  --gateway-identifier $(python3 ../scripts/id.py gateway) --query gatewayUrl --output text)
curl -s -o /dev/null -w "HTTP %{http_code}\n" -X POST "$GATEWAY_URL/mcp" \
  -H "Content-Type: application/json" -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'
    Cosa dovresti vedere HTTP 401, cioè autenticazione mancante. Il comando agentcore invoke del passo prima funzionava perché il CLI firma la richiesta con le tue credenziali.

  8. Ora prova l'agente. Giulia ha una fattura di ottobre più alta del solito.

    python3 ../scripts/chiedi.py --utente giulia --sessione fattura "Sono Giulia Bianchi, codice cliente C002. La fattura di ottobre mi sembra alta, potete controllare?"
    Cosa dovresti vedere 
    [strumento] crm___get_fatture
[strumento] crm___get_cliente
Giulia, ho controllato e ha ragione. La fattura di ottobre 2026 (F2026-1021) è di 29,98 euro,
il doppio di settembre: il canone di ottobre è stato addebitato due volte. ...
    L'agente ha trovato da solo l'addebito doppio leggendo i dati del CRM. Probabilmente ti propone un accredito: tienilo da parte, è l'argomento del Lab 4.

Identity: chi autentica chi

Concetto: AgentCore Identity

Identity gestisce due lati. In ingresso decide chi può chiamare un agente o un Gateway: con IAM, come qui, oppure con token JWT di un provider di identità. In uscita fornisce all'agente o al Gateway le credenziali per chiamare altri sistemi: un ruolo IAM, una chiave API o un token OAuth. Le chiavi e i segreti OAuth stanno in un archivio di AgentCore Identity, non nel codice né nelle variabili d'ambiente.

Nel percorso che hai appena costruito ogni passaggio ha la sua autenticazione:

DaACome si autentica
Tu, dal terminaleRuntimeIAM: il CLI firma la richiesta con le tue credenziali AWS
RuntimeGatewayIAM: il ruolo di esecuzione del Runtime, a cui il deploy ha dato il permesso di chiamare il Gateway
GatewayLambda del CRMIAM: il ruolo del Gateway, con il permesso di invocare la Lambda

Il ruolo del Runtime ha anche il permesso bedrock-agentcore:GetWorkloadAccessToken. Ogni agente ha una sua identità di workload in AgentCore Identity: è con questa identità che il codice dell'agente può chiedere all'archivio una chiave API o un token OAuth, quando ne ha bisogno.

Per un'API esterna che vuole una chiave, la chiave si registra in AgentCore Identity e il target del Gateway la usa al posto tuo. Il tutorial ufficiale lo fa con un'API della NASA:

esempio dal tutorial ufficiale, non serve eseguirlo
printf 'DEMO_KEY' | agentcore add credentials api-key --name nasa --api-key -

Il CLI rifiuta le chiavi scritte nel comando: si passano sullo standard input, così non restano nella cronologia della shell. Trovi l'esempio completo nella sezione Tools del tutorial ufficiale.
